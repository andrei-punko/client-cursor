# Как работает OFFSET-пагинация

Клиент передаёт:

- `LIMIT` — сколько записей вернуть
- `OFFSET` — сколько записей пропустить

Пример: `OFFSET = 2`, `LIMIT = 2`  
→ БД читает 4 строки, отбрасывает первые 2, отдаёт следующие 2.

<!--
Начнём с того, как устроен привычный paging на основе OFFSET.

Клиент говорит: дай мне LIMIT записей, начиная с позиции OFFSET. На слайде маленький пример: offset два, limit два. На практике это часто offset четыреста, limit двадцать — в итоге получается «двадцать первая страница».
-->

# Как работает OFFSET — SQL

```sql
SELECT * FROM items
ORDER BY id
LIMIT 2 OFFSET 2;
```

→ вернёт `Cat`, `Dan`

<!--
Интуиция такая: «просто прыгни на нужное место». Но для многих СУБД это выглядит иначе: нужно прочитать и отсортировать строки вплоть до OFFSET плюс LIMIT, а потом отбросить первые OFFSET. То есть при глубокой странице вы платите за работу, результат которой клиенту даже не отдаёте.
-->

---

# Почему OFFSET ломается

**Производительность**

- Чем больше `OFFSET`, тем дороже запрос
- БД всё равно проходит «хвост» до `OFFSET + LIMIT`

**Стабильность окна**

- При частых вставках страница «плывёт»
- Возможны пропуски и дубликаты между страницами

→ Нужен seek по позиции, а не по номеру страницы

<!--
Отсюда два практических минуса.

Первый — производительность. Чем дальше страница, тем тяжелее запрос. На больших таблицах получение «страницы 500» может быть заметно медленнее получения «страницы 1», даже при том же LIMIT.

Второй — стабильность. Пока пользователь листает, в таблицу могут вставляться новые строки. Окно, заданное номером страницы, начинает плыть: часть записей пользователь увидит дважды, часть — пропустит.
-->

# Идея Client Cursor API

В ответе — **маркер (cursor)**: непрозрачная ссылка на позицию в датасете.

Клиент для следующей порции:

- передаёт `cursor` из прошлого ответа
- получает записи **после** (или **до**) этой позиции

Вместо «страница 21» — только **next** / **prev**.

<!--
Так появляется идея Cursor API.
Подчеркну, что речь о клиентском курсоре, т.к. есть еще курсор в БД, о нем сейчас речь не идет.

Сервер в ответе возвращает маркер — курсор. Это непрозрачная для клиента строка, которая ссылается на место, где мы остановились. В следующем запросе клиент передаёт этот маркер и просит порцию после него — или до него, если идём назад.

Модель меняется: вместо «дай страницу номер N» — говорим «дай следующую» и «дай предыдущую». Для бесконечного скролла это обычно то, что нужно.
-->

---

# Sequential ID — tie-breaker

Одного `author` мало — значения повторяются:

<table class="example">
  <thead>
    <tr><th>id</th><th>author</th><th></th></tr>
  </thead>
  <tbody>
    <tr><td>37</td><td>John</td><td></td></tr>
    <tr class="anchor"><td>38</td><td>John</td><td>← курсор здесь</td></tr>
    <tr class="page2"><td>39</td><td>John</td><td>следующая порция</td></tr>
    <tr class="page2"><td>40</td><td>Zed</td><td></td></tr>
  </tbody>
</table>

Курсор хранит: `author` **+** `id` → однозначный seek.

<!--
Важный нюанс: одного поля сортировки часто мало.

Несколько статей могут быть от одного автора. Если запомнить только «мы остановились на John», непонятно, с какой именно записи John продолжать.

Поэтому нужен sequential id — монотонный идентификатор: числовой первичный ключ, serial, bigserial. В курсоре храним author и id крайней записи. При равных значениях sort-поля двигаемся по id.
-->


В нашем демо это GET /articles с sort=author, order=ASC и size=2. К базе уходит ORDER BY по полю сортировки и по id, плюс LIMIT.
-->

Если вернулось меньше, чем size, мы у края ленты — next можно не отдавать.

# Forward cursor — запрос

```http
GET /articles?size=2&cursor=eyJmIjp0cnVl...
```

```sql
SELECT * FROM articles
WHERE (author = :v AND id > :i)
   OR author > :v
ORDER BY author, id
LIMIT 2;
```

<!--
Дальше клиент берёт next cursor и передаёт его в следующем запросе.

Сервер декодирует cursor и строит seek-условие. В упрощённом SQL для сортировки по возрастанию: либо то же значение поля и больший id, либо строго большее значение поля. Плюс снова ORDER BY и LIMIT.
-->

# Forward cursor — payload

В `next` до Base64:

```json
{ "f": true, "i": 38, "n": "author", "v": "John", "o": "ASC" }
```

В ответе уже могут быть и `prev`, и `next`.

<!--
Внутри курсора до кодировки в Base64 — компактный JSON. В проекте ключи короткие:
- f — направление вперёд,
- i — id, 
- n и v — имя и значение поля сортировки,
- o — порядок ASC или DESC.
Клиенту это разбирать не обязательно: для него курсор — просто строка из прошлого ответа.

В ответе на вторую страницу уже могут появиться и prev, и next.
-->

---

# Backward cursor — запрос

```http
GET /articles?size=2&cursor=eyJmIjpmYWxzZ...
```

```sql
SELECT * FROM articles
WHERE (author = :v AND id < :i)
   OR author < :v
ORDER BY author DESC, id DESC
LIMIT 2;
```

После выборки — **reverse** списка, чтобы клиент видел тот же порядок, что при чтении вперёд.

<!--
Обратный курсор — зеркальная история.

Клиент передаёт prev из прошлого ответа. Условие «меньше»: либо тот же author и меньший id, либо строго меньший author. В БД сортировка по убыванию, LIMIT тот же. Затем результат разворачиваем — клиент получает записи в ожидаемом порядке.
-->

---

# Backward cursor

Сейчас на экране `John/39`, `Zed/40`.  
`prev` построен от **первой** записи страницы (`39`).

  </thead>

В БД: `ORDER BY … DESC` + `LIMIT`, затем **reverse** для клиента.

<!--
Обратный курсор — зеркальная история.

Условие «меньше», сортировка в запросе к БД — по убыванию, LIMIT тот же. Но клиенту мы отдаём список в ожидаемом порядке чтения вперёд, поэтому после выборки результат разворачиваем.

prev строится от первой записи текущей страницы и помечается как backward — параметр f равен false. Так клиент ходит туда-сюда относительно текущей позиции, не считая номера страниц.
-->

# Параметры внутри курсора

После первого запроса:

```http
GET /articles?size=2&cursor=...
```

| ключ | смысл           |
|------|-----------------|
| `f`  | forward?        |
| `i`  | sequential id   |
| `n`  | sort field name |
| `v`  | sort value      |
| `o`  | ASC / DESC      |

Клиент курсор не парсит — это "просто строка".

<!--
Удобный приём: упаковать параметры запроса в сам курсор.

После первого запроса клиенту достаточно передавать size и cursor (на выбор - next или prev). Sort и order уже внутри курсора — их не нужно повторять в query string, и нельзя случайно пересортировать середину ленты другим полем.

В нашем проекте это жёстко: если курсор уже есть, sort в query передавать нельзя — либо в параметре, либо внутри курсора.
-->

# Демо: client-cursor

`GET /articles` → `{ "data", "prev", "next" }`

```bash
curl 'http://localhost:9080/articles?size=2&sort=author'

curl 'http://localhost:9080/articles?size=2&cursor=...'
```

<!--
Коротко про демо client-cursor.

Это Spring Boot REST на порту 9080. Листинг статей: GET /articles, ответ data, prev, next.

Первый запрос: curl с size=2 и sort=author. Во втором — тот же size и cursor из next или prev.
-->

---

# Демо: правила

- `sort` / `order` — только в **первом** запросе
- `size` можно менять на каждом запросе
- `next = null`, если `data.size < size`
- `prev = null`, если в запросе нет `cursor` или `data` пустой
- sort: `title` | `author` | `summary`
- Swagger: `localhost:9080/swagger-ui`

<!--
Правила, которые полезно помнить: sort только на старте; size можно менять; next становится null, когда данных меньше size; prev равен null, если в запросе нет cursor или data пустой. Sort-поля ограничены whitelist: title, author, summary. Sequential id здесь — обычный generated Article.id. Подробности и Swagger — по ссылкам в описании.
-->

# Итоги

Cursor API даёт:

- стабильный seek без глубокого `OFFSET`
- меньше сюрпризов при вставках во время листания

Ограничение:

- удобные переходы **next / prev**, а не «страница N»
